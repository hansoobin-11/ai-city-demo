# SPACEBANK AI CITY 전시 UI 작업 규칙

## 작업 방식

- 규모 있는 변경은 구현 전에 범위, 변경 대상, 검증 방법을 짧게 제시하고 방향을 확인한다.
- UI 요청이 두 가지 이상으로 해석되면 기존 레퍼런스와 확정본을 먼저 대조한다. 그래도 모호하면 구현 전에 질문한다.
- 외부 데이터나 백엔드가 확정되지 않았으면 mock으로 화면과 흐름부터 검증한다.
- 변경은 작은 체크포인트로 나누고, 실제 전시 모니터에서 확인 가능한 단위로 마무리한다.
- 사용자가 자동 동작을 요구하면 `무슨 사건이 발생했을 때 무엇을 실행하는지`를 구체적인 트리거로 정의한다. 단순히 "자동으로 처리한다"고만 적지 않는다.
- 되돌리기 어려운 변경, 실제 데이터 변경, 여러 사람이 공유하는 대상의 변경은 계획과 승인 단계를 먼저 거친다. 스타일·mock·문서처럼 되돌리기 쉬운 변경은 별도 승인 대기 없이 요청 범위 안에서 진행한다.

## 전시 UI 불변 조건

- TOP, LEFT, CENTER, RIGHT는 하나의 공통 시간축을 사용한다.
- 각 출력 창은 자기 화면만 렌더링한다. 다른 화면을 함께 렌더링한 뒤 CSS로 잘라내는 방식을 최종 구조로 사용하지 않는다.
- 확장 디스플레이에서 창 배치는 사람이 수행하고, 통합 라우터는 창 열기와 재생·일시정지·처음으로 동기 제어를 담당한다.
- 최종 실행본은 네트워크 없이 동작해야 한다. 외부 CDN, 원격 폰트, 원격 API에 의존하지 않는다.
- 작업용 프로젝트와 전시용 오프라인 빌드를 분리한다. 배포물은 `offline/`에 생성한다.
- 색감은 노트북과의 일치보다 LEFT·CENTER·RIGHT 사이 연결감을 우선한다.
- 밝은 전시장에서도 메인 카피, 센서, 연결선이 보이도록 밝은 환경용 표시 모드를 제공한다.

## 검증

- 상태나 완료 여부를 말하기 전에 실제 파일, 실행 화면, 테스트 결과를 확인한다.
- 사용자가 신고한 증상은 가능한 한 동일한 환경에서 재현한 뒤 원인을 확정한다. 재현하지 못했으면 추정이라고 밝힌다.
- 성능은 네 화면 동시 실행 상태에서 확인한다. 단일 창 결과만으로 전시 성능을 판단하지 않는다.
- 긴 도구 작업이나 반복 검증 전에는 무엇을 왜 확인하는지 짧게 알린다.

## 결과물과 권한 경계

- 검토 요청은 파일 수정 승인으로 간주하지 않는다. 검토 결과와 실제 반영을 구분한다.
- 도메인 전문가나 실제 이해관계자가 정해야 하는 분류·우선순위·가중치를 임의로 만들어 채우지 않는다.
- 사용자가 특정 판단의 권한이 도메인 전문가나 이해관계자에게 있다고 정하면 설계 편의를 이유로 그 권한을 AI 쪽으로 되돌리지 않는다.
- PR 생성과 머지는 사용자가 수행한다. 요청받은 경우 제목·본문 초안과 로컬 변경까지만 준비한다.
- 공유용 요약이나 인수인계는 별도 파일 요청이 없으면 채팅에서 복사 가능한 자연스러운 한국어로 제공한다.
